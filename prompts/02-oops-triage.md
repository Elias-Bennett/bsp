# 提示词 02 · oops / panic 分诊

**什么时候用**：内核崩溃、panic、WARN、lockdep、RCU stall、soft lockup。

**怎么用**：
1. 抽取现场（比直接贴全量日志准确得多）：
   ```bash
   ./bsp/board.sh oops logs/boot-xxx.log > oops.txt
   ```
2. **必须提供 vmlinux**（未被 strip 的那个），否则模型只能猜函数名，价值减半。
   如果不想上传二进制，至少提供：
   ```bash
   # 崩溃 PC 附近的符号
   aarch64-linux-gnu-addr2line -f -e vmlinux 0xffffffc0xxxxxxxx
   # 或整条调用栈批量解析
   aarch64-linux-gnu-addr2line -f -e vmlinux $(日志里提取的地址列表)
   ```
3. 把 `oops.txt` + 解析结果 + 相关源码文件一起给模型。

```text
你是内核崩溃分析专家。下面是一次 ARM64 Linux 的崩溃现场。

## 环境
- 内核版本: <uname -r 输出，如 6.1.55>
- 架构: <arm64 / arm>
- 板子 / SoC: <...>
- 崩溃可复现性: <必现 / 概率 / 只在特定操作后>
- 最近改动: <改了哪个驱动 / DTS / 无>

## 崩溃现场
<粘贴 oops.txt 内容>

## 符号化结果（addr2line 输出，如果有）
<粘贴>

## 相关源码
<把崩溃函数所在文件贴进来，或告诉我用 grep 找哪个符号>

---

## 要求

### 1. 崩溃分类（先给结论）
从下面选一个，并说明依据：
- NULL 指针解引用 / 野指针
- 访问已释放内存（UAF）
- 栈溢出 / 越界写
- 显式 BUG_ON / WARN_ON 断言
- 死锁（lockdep 报告）
- 中断上下文违规（在 atomic 上下文睡眠）
- 硬件访问异常（寄存器访问触发外部 abort）
- 内存耗尽（OOM）
- 无法从现场判断（说明还缺什么证据）

### 2. 定位
- 崩溃函数：`<函数名>` @ `文件:行号`
- 触发路径：从 `Call trace` 反推，画出调用链（用箭头表示，标出哪一跳是跨模块的）
- 直接原因 vs 根因：明确区分。**PC 停在哪 ≠ bug 在哪**，多数情况下崩溃点只是受害者。

### 3. 假设与验证
给 3 个假设，每个包含：
| 假设 | 支持证据 | 证伪实验 | 修复方向 |

### 4. 需要的额外信息
按优先级列出，最多 5 条。每条说明"为什么需要"和"怎么拿到"：
- 例：需要 `CONFIG_DEBUG_KMEMLEAK=y` 的日志 —— 用来区分 UAF 和野指针
- 例：需要 `cat /sys/kernel/debug/kmemleak`
- 例：需要该驱动的 `probe` 函数源码 —— 用于检查错误路径是否漏了释放

### 5. 修复草案
给最小修复（minimal fix），不要顺手重构。标注：
- 这个修复能否解释所有现象？
- 有没有可能只是掩盖了症状？
- 需要什么回归测试来防止复发？

## 硬约束
- 不要编造函数名和行号。不确定的地方写"需要确认"。
- 引用日志必须带行号。
- 如果现场信息不足以定位，直接说"信息不足"，并给出采集方案。
```

## 补充：让模型做「版本对照」也很有效

```text
这个驱动在 upstream v6.1 和 v6.6 之间有哪些修复？用 git log 的方式列出。
如果不知道具体 commit，说明"需要你在本地 kernel 仓库执行：

    git log --oneline v6.1..v6.6 -- drivers/<子系统>/

然后把输出贴给我"。

不要凭印象编造 commit hash。
```

# 提示词 03 · 驱动代码 review

**什么时候用**：写完/改完一个驱动，上板之前先过一遍。这是 AI 性价比最高的用法之一 ——
模式化缺陷（错误路径泄漏、锁顺序、DMA 配对）它比人更不容易漏。

**怎么用**：把驱动文件 + DTS 节点 + 对应的 binding YAML 一起给模型。

---

```text
你是 Linux 内核维护者，review 下面这个驱动。目标是找出**会导致上板后不稳定、
但编译能通过**的问题，不是风格问题。

## Review 清单（逐条给结论，不要跳过）

### A. 资源与生命周期
1. `probe` 的每个失败路径：已获取的资源是否全部释放？`devm_*` 托管了哪些、哪些是手动的？
2. `remove` 是否真的停掉硬件（关时钟、断 DMA、禁中断、复位芯片），而不只是注销设备？
3. 有没有在 `probe` 里启动的异步工作（工作队列/定时器/线程）没在 `remove` 里停掉？
4. `of_node_put` / `clk_put` / `regulator_put` 是否配对？

### B. 并发
5. 中断处理函数与进程上下文共享的数据，保护手段是什么？够不够？
6. `spin_lock` 临界区里有没有可能睡眠的调用（`msleep`、`regmap` 走 I2C 的慢访问、`kmalloc(GFP_KERNEL)`）？
7. `probe` 与 `remove`、`suspend` 与 `resume` 之间有没有竞态窗口？
8. 有没有在中断上下文里调用 `dev_err` 之外的 printk 重活？有没有用 `printk` 但没限速？

### C. 硬件访问
9. 寄存器读写是否统一走 `regmap` 或 `readl/writel`？有没有裸指针直接解引用 IO 内存？
10. 位域操作用的是 `FIELD_PREP` / `regmap_update_bits` 还是手写掩码？手写的掩码有没有错？
11. ARM64 上有没有把 32 位值当地址用、或 `unsigned long` 与 `u32` 混用导致的截断？
12. 有没有假设"读-改-写"是原子的，但硬件可能是 write-1-to-clear？

### D. 电源管理
13. `runtime_suspend` / `runtime_resume` 是否成对？引用计数是否平衡（`pm_runtime_get/put`）？
14. `suspend` 顺序是否正确：先停数据流（DMA/中断），再关时钟，最后断电？`resume` 严格反序？
15. 恢复后是否需要重新初始化硬件（有些芯片掉电后寄存器全丢）？

### E. DMA
16. `dma_map_*` 与 `dma_unmap_*` 是否严格配对？错误路径上也配了吗？
17. buffer 在 DMA 传输期间会不会被 `kfree` 或复用？
18. 一致性 DMA 与流式 DMA 是否用对了（`dma_alloc_coherent` vs `dma_map_single`）？

### F. 错误处理
19. `IS_ERR` / `PTR_ERR` 判断有没有写反？`if (!IS_ERR(x))` 这种反逻辑？
20. 返回值有没有被忽略（尤其 `regmap_write`、`clk_prepare_enable`）？
21. 错误信息是否带足够上下文（设备名、寄存器值、出错步骤）？

### G. DT / 匹配
22. `compatible` 字符串与 binding YAML 一致吗？
23. 是否正确用了 `device_property_read_*`，而不是自己解析 `of_` 私有属性？
24. 必需属性缺失时的行为是"报错退出"还是"用默认值静默继续"？后者往往是坑。

## 输出格式

一个表格，只列**有问题的项**：

| # | 严重度 | 位置 | 问题 | 为什么会在上板时出问题 | 修复 |
|---|---|---|---|---|---|
| 12 | 高 | `xxx.c:145` | ... | ... | ... |

严重度定义：
- **高**：会导致崩溃、数据损坏、偶发不稳定
- **中**：特定场景才触发（suspend/resume、错误注入、热插拔）
- **低**：不影响功能，但会误导后来的人

然后给一段「结论」：这个驱动现在能不能上板？如果能，**必须**先跑哪三个验证？

## 硬约束
- 只评论你在这个文件里**实际看到**的代码，不要假设"大概还写了什么"。
- 不要提纯风格问题（命名、行宽、注释格式），除非它影响可读性到会引发 bug。
- 不确定的要写"需要确认"，不要编。
```

## 变体：让模型扮演"挑刺的维护者"做二轮

第一轮 review 之后，追加：

```text
现在换个角度：假设这个驱动已经在量产板子上跑了一个月，客户报了
"偶发死机，一天一两次，重启就好"。

基于你刚才看到的代码，列出**最可能的 3 个**偶发问题，
并说明每个要用什么手段才能抓到现场（ftrace / KASAN / lockdep / 加日志）。

不要重复第一轮已经指出的确定性问题，专注"偶发、难复现"这一类。
```
